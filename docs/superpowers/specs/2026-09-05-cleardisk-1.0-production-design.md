# ClearDisk 1.0 production release — design

Date: 2026-09-05. Status: approved in brainstorming, awaiting implementation plan.

## 1. Goal

Turn the working ClearDisk prototype into a sellable 1.0 for direct download:
scanning stays free, every removal action unlocks with a $10 one-time license
bought on cleardisk.app through Stripe. Ship dark mode, a single safe removal
flow with real feedback, a scan that shows its hero screen fast on slow Macs,
and the website that sells it.

### In scope

1. License backend: Cloudflare Worker + KV + Stripe + Cloudflare Email Sending.
2. In-app licensing: activation, offline verification, one gate, unlock sheet.
3. Removal flow: one confirmation sheet for every removal, impact block,
   "No, keep it" default for irreversible actions, purge-from-Trash checkbox,
   result view, Empty Trash.
4. Dark mode via an adaptive palette that follows the system, plus a button
   system with hover/press/disabled/focus feedback and small polish items.
5. Two-pass home scan (hero first) with live per-bucket findings while scanning.
6. Website: landing, buy-now, thanks, recover, download, three SEO pages,
   privacy, terms.
7. Direct 1.0 release through the existing notarized-DMG scripts.

### Out of scope (later specs)

- Mac App Store edition (sandbox, StoreKit, second target). Section 10 lists
  what it will need so nothing here blocks it.
- Sparkle auto-update. 1.0 has a "Check for Updates" menu item that opens the
  download page.
- Persistent scan cache / incremental rescans.
- Admin UI for licenses. Owner edits use `wrangler kv`.
- Self-service deactivation. Support frees a slot with one KV edit.

## 2. Decisions locked in this brainstorm

| Topic | Decision |
|---|---|
| Payment | Stripe, embedded Checkout on cleardisk.app/buy-now, $10 USD one-time. Stripe Tax is a toggle the owner can turn on; the code passes `automatic_tax` from config. |
| License model | Short key `CLDK-XXXX-XXXX-XXXX-XXXX`, online activation once, offline forever after. |
| Backend | One Cloudflare Worker serving the static site as assets and `/api/*` routes, KV for license records, Cloudflare Email Sending for key emails. Domain cleardisk.app is on Cloudflare DNS. |
| Activations | 3 Macs per key, identified by hardware UUID. |
| Refunds | 30-day money-back on the buy page. Full refund or dispute revokes the key automatically. |
| Price display | "$10" everywhere on the site and in the app (one constant). App Store edition later will use Apple's $9.99 tier. |
| Dark mode | Adaptive palette keeping the approved design; follows System Settings; Settings window offers System / Light / Dark. |
| Scan | Two-pass home scan, hero first; live bucket totals during scan. |
| Checkout | Stripe embedded Checkout (Apple Pay, Link, card). Stripe collects the email; we collect nothing else. |
| Removal safety | Unchanged: trash by default, deny-by-default blocklist, permanent deletion only inside `TrashService`, enforced by the build script. |

## 4. License backend (web/)

One Worker, TypeScript, deployed with `wrangler deploy`. Static files in
`web/public/` are served through the assets binding; anything under `/api/`
is handled by the router in `web/src/index.ts`.

### 4.1 Routes

| Route | Caller | Behaviour |
|---|---|---|
| `POST /api/checkout` | buy-now page | Creates a Stripe Checkout Session: `ui_mode: "embedded"`, the single Price id, `return_url: https://cleardisk.app/thanks?session_id={CHECKOUT_SESSION_ID}`, `automatic_tax` from config. Returns `{ clientSecret }`. |
| `POST /api/stripe/webhook` | Stripe | Verifies the signature with the webhook secret. `checkout.session.completed` with `payment_status == "paid"` → `issueKey(session)`. `charge.refunded` with `refunded == true` (full refund) and `charge.dispute.created` → revoke the key found through the payment-intent index. Everything else → 200, ignored. |
| `GET /api/key?session_id=` | thanks page | Looks up `session:<id>`. On a miss it retrieves the session from Stripe; if paid, runs `issueKey(session)` itself. Returns `{ key, email }` or 404 while unpaid. |
| `POST /api/activate` | the app | Body `{ key, machineId, machineName, appVersion }`. Normalizes the key. 404 unknown, 403 revoked, 409 when three other machines are registered (body lists their names), else records or refreshes the activation and returns the signed receipt. |
| `POST /api/recover` | recover page | Body `{ email }`. Always 200 with the same message. If `email:<lowercased>` exists and the key is active, re-sends the key email. |

Rate limiting is a Cloudflare WAF rate-limiting rule on `/api/*` (20 requests
per minute per IP), configured in the dashboard, not in code.

### 4.2 Key derivation

```
digest = HMAC-SHA256(KEY_SECRET, "cleardisk:v1:" + session.id)
key    = "CLDK-" + crockford32(digest[0..10]) grouped as XXXX-XXXX-XXXX-XXXX
```

Crockford base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. 80 bits from
the digest gives 16 characters. The canonical form, used everywhere a key is
stored, compared or displayed, is `CLDK-` plus the 16 characters in four
dash-separated groups. Normalization (same function on server and in the
app) turns any pasted text into the canonical form or nil: uppercase, map
O→0, I→1, L→1, strip everything that is not A–Z or 0–9, drop a leading
`CLDK`, require exactly 16 characters, re-group. Because the key is a
pure function of the session id, the webhook and the thanks page can both
issue for the same session and produce one identical key; `issueKey` is
idempotent by construction.

### 4.3 KV (`LICENSES` namespace)

| Key | Value |
|---|---|
| `key:<KEY>` | `{ key, email, sessionId, paymentIntent, status: "active" \| "revoked", createdAt, revokedAt?, activations: [{ machineId, machineName, activatedAt, lastSeenAt, appVersion }] }` |
| `email:<lowercased email>` | `<KEY>` (a repeat purchase overwrites; last key wins) |
| `pi:<payment_intent id>` | `<KEY>` (refund and dispute lookup) |
| `session:<checkout session id>` | `<KEY>` (thanks-page lookup) |

`issueKey` writes all four entries. Revocation sets `status: "revoked"` and
`revokedAt`. Owner maintenance (free an activation slot, revoke by hand) is a
`wrangler kv key get/put` against `key:<KEY>`.

### 4.4 Signed activation receipt

Message: `"cleardisk:v1:" + key + ":" + machineId`. The Worker signs it with
an Ed25519 private key (WebCrypto `Ed25519`). Response:

```json
{ "key": "CLDK-…", "email": "…", "machineId": "…", "activatedAt": "…", "signature": "<base64>" }
```

The app embeds the matching public key and verifies offline on every launch.
The private key never leaves Worker secrets.

### 4.5 Email

Cloudflare Email Sending binding `EMAIL`, from `hello@cleardisk.app`
(SPF, DKIM and DMARC records for cleardisk.app are part of go-live).
Subject: "Your ClearDisk license key". Plain text plus a minimal HTML part.
Body: the key, a button/link `cleardisk://activate?key=<KEY>`, the download
link `https://cleardisk.app/download`, the recover link, the 3-Mac rule, and
the support address. Sent by `issueKey` and by `/api/recover`.

### 4.6 Secrets and config

Secrets (`wrangler secret put`): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
`KEY_SECRET`, `LICENSE_SIGNING_KEY` (PKCS8 Ed25519). Vars in `wrangler.jsonc`:
`STRIPE_PRICE_ID`, `SITE_URL`, `AUTOMATIC_TAX` ("true"/"false"),
`MAX_ACTIVATIONS` (3). Bindings: `LICENSES` (KV), `EMAIL`, `ASSETS`.

### 4.7 Tests (web/test, vitest with the Workers pool)

- Key derivation is deterministic and matches the format; normalization maps
  the confusable characters.
- Activate: unknown → 404, revoked → 403, same machine twice → one entry,
  fourth machine → 409 listing the three names.
- Webhook: bad signature → 400; paid session issues the four KV entries;
  full refund revokes; partial refund does not.
- Receipt signature verifies with the public key and fails when the message
  is altered.

Manual: `stripe listen --forward-to localhost:8787/api/stripe/webhook` and
`stripe trigger checkout.session.completed`.

## 5. Licensing inside the app

### 5.1 `LicenseStore` (`Sources/ClearDiskApp/License.swift`)

`@MainActor @Observable final class LicenseStore` with
`enum State { case free; case licensed(key: String, email: String) }` and
`var isLicensed: Bool`. Injected into the environment next to `AppState`.

Storage: `~/Library/Application Support/ClearDisk/license.json`, file mode
0600, fields `key, email, machineId, activatedAt, signature, lastCheckedAt`.

Launch: read the file, verify `signature` over
`"cleardisk:v1:" + key + ":" + currentMachineId` with the embedded Ed25519
public key (CryptoKit `Curve25519.Signing.PublicKey`). Valid → licensed.
Missing, unreadable, tampered or a different machine → free. No network.

Machine id: `IOPlatformUUID` from `IOPlatformExpertDevice` (IOKit).
Machine name: `Host.current().localizedName ?? "Mac"`.

`activate(rawKey:) async throws`: normalize (same rules as the server),
`POST /api/activate`, store the receipt, set state. Errors are an enum with
user-facing text: `invalidKey` ("That key isn't recognised. Check for typos or
use Recover on cleardisk.app"), `revoked` ("This key was refunded"),
`limitReached(names)` ("Already in use on 3 Macs: … . Email support to free a
slot"), `offline` ("Couldn't reach cleardisk.app. Check your connection and
try again", with Retry).

Weekly recheck: on launch, if `lastCheckedAt` is older than 7 days, fire
`POST /api/activate` for the same machine in the background. 403 or 404 →
delete the file and go free (with a toast "Your license is no longer active").
Any other failure → nothing changes.

### 5.2 Deep link

`Info.plist` registers URL scheme `cleardisk`. The app handles
`cleardisk://activate?key=…` through `.onOpenURL`: open the unlock sheet with
the key pre-filled and start activation immediately.

### 5.3 The one gate

`RemovalSheet` (section 6) is the only place removal is confirmed. Its
presenter checks `license.isLicensed`. Free users see the unlock sheet instead
of the confirmation; the pending `RemovalRequest` is kept, and when activation
succeeds the unlock sheet closes and the confirmation for that request opens.
All Trash / Delete / Clean buttons stay visible and enabled for free users.

### 5.4 Unlock sheet (`UnlockSheet.swift`)

- Headline with the number in hand: "Reclaim 23.4 GB. Unlock ClearDisk for
  $10." (falls back to "Unlock ClearDisk for $10" when opened from the menu).
- Bullets: one-time payment, no subscription · use on 3 Macs · 30-day
  money-back · notarized by Apple, runs entirely offline.
- Primary button "Buy for $10" opens
  `https://cleardisk.app/buy-now?reclaim=<GB>&ref=app` in the browser and the
  sheet switches to "Waiting for your key… paste it below or click Activate in
  the email".
- Secondary "I have a key": paste field (accepts any formatting), Activate
  button with spinner, inline error text with Retry when offline.
- Success state: "You're all set, licensed to <email>" for one second, then
  the sheet closes and the pending confirmation opens.

### 5.5 Elsewhere

- Sidebar card: free → "Unlock cleaning — $10 once" button opening the unlock
  sheet; licensed → "Licensed to <email>".
- App menu: "License…" opens the unlock sheet; "Check for Updates…" opens
  `https://cleardisk.app/download`.
- `enum Pricing { static let display = "$10"; static let buyURL = … }`
  replaces every "$9.99" string.

### 5.6 Tests (`Tests/ClearDiskAppTests`)

The test target generates its own Ed25519 keypair and injects the public key.
- Receipt valid → licensed; altered signature → free; different machine id →
  free.
- Key normalization: lowercase, spaces, O/I/L confusables, missing `CLDK-`.
- Gate: free + request → unlock sheet presented, request retained; licensed →
  confirmation presented.

## 6. Removal flow

### 6.1 Model (`RemovalSheet.swift`)

```swift
struct RemovalItem { name, path, size: Int64, isDirectory, contentsOnly: Bool }
enum RemovalMode { case trash, forever }
struct RemovalRequest { items: [RemovalItem]; mode: RemovalMode; title: String? }
struct RemovalOutcome { trashed: [TrashService.TrashedItem]; trashedBytes; freedBytes; failures: [(name, reason)] }
// freedBytes = bytes no longer on disk (forever + purged); trashedBytes = still in the Trash
```

`contentsOnly` covers the System Data rows that clean the contents of a cache
root while keeping the folder. Empty Trash is a request in `.forever` mode
whose items are the children of `~/.Trash`. Like every removal it runs through
the sheet, so it is license-gated too.

Call sites that build a request and present the sheet: FileRowsView (Large
Files, Search), BrowserView, TreemapView, SystemDataView (Clean Safely),
ReclaimableView (Clean Selected), Sidebar Trash card (Empty Trash). The old
`confirmationDialog`s and `DeleteForeverSheet` are removed.

### 6.2 Confirmation (single step)

- Title: "Move 3 folders (4.2 GB) to the Trash?" / "Delete node_modules
  (1.8 GB) forever?" / "Empty the Trash (6.1 GB)?".
- Impact block: scrollable item list with sizes (capped at 200 rows with
  "+N more"), total, and the free-space line "24.1 GB free now → 28.3 GB
  after". For trash-only the line reads "24.1 GB free now · frees when the
  Trash is emptied".
- Checkbox (trash mode only): "Also remove from Trash now — frees the space
  immediately, can't be undone". Last choice remembered in
  `UserDefaults["purgeAfterTrash"]`, default off.
- Type-the-name confirmation is gone.

### 6.3 Buttons follow reversibility

| Situation | Default (highlighted, Return) | Other button | Escape |
|---|---|---|---|
| Trash, checkbox off | "Move to Trash" (blue) | "Cancel" | cancels |
| Trash, checkbox on | "No, keep it" | "Yes, delete" (red) | keeps |
| Forever / Empty Trash | "No, keep it" | "Yes, delete" (red) | keeps |

Irreversible variants show "This cannot be undone." under the buttons.

### 6.4 Execution and result

Execution runs on a background task; the sheet shows a progress indicator
with "Removing 3 of 12…". Then it flips to the result view:
- Large figure: "4.2 GB freed" (forever or purged) or "4.2 GB moved to the
  Trash".
- "Free space: 28.3 GB" (fresh read from the volume).
- Undo button when items are still in the Trash (uses the existing restore
  path); Done button otherwise.
- Failures listed by name with reason ("in use", "protected", "permission
  denied"); never collapsed into a suffix.

The existing bottom toast keeps its role as the lingering Undo after the
sheet is dismissed.

### 6.5 Refresh right away

`AppState.applyRemoval` gains a `purged: Bool`: trash-only grows the `.Trash`
node as today; purged or forever subtracts from totals and, for purged, also
shrinks the `.Trash` node. After every outcome: `refreshVolumeInfo()`, sidebar
donut and totals animate with `.numericText`, Trash card updates or hides.
No rescan.

### 6.6 `TrashService` additions

- `purgeFromTrash(_ items: [TrashedItem]) -> (purged: Int, failed: [(URL, Error)])`
  — refuses any URL whose standardized path does not start with
  `<home>/.Trash/`.
- `emptyHomeTrash() -> (purged: Int, bytes: Int64, failed: …)` — lists
  `~/.Trash` children and purges them.
- `deleteForever` unchanged. `FileManager.removeItem` still appears only in
  this file; the build-script guard stays.

### 6.7 Tests

- Purge refuses a path outside `~/.Trash`; trash-then-purge round trip in a
  temp directory frees the file.
- Default-button rule per mode/checkbox.
- Each screen builds the expected request (System Data rows → contentsOnly).

## 8. Scan: hero first, live findings

### 8.1 Two-pass home scan (`AppState`)

Only for scans whose path is the home folder.
- Pass 1: `ParallelScan.scan(path: home, skipPrefixes: <every top-level
  directory of home that is not "Library" and does not start with ".">)`.
  Top-level files are counted here.
- On completion: `root = pass1.root`, `homeNode = root`, build the report and
  category totals, `phase = .done`, `isPartial = true`, show System Data.
- Pass 2: `ParallelScan.scan(path: home, skipPrefixes: <"Library" and every
  dot-directory>)`. Its top-level files are dropped and their sizes and
  counts subtracted from the pass-2 stats (pass 1 already counted them).
- Graft on the main actor: append pass-2 root children to the live root,
  recompute root size, merge stats, `isPartial = false`, `treeVersion += 1`,
  rebuild derived data.
- Cancellation: `ParallelScan.Engine` gets a cancel flag checked in the pop
  loop; Rescan or quit during pass 2 cancels it and discards its result.

Cleaning during pass 2 is safe: surgery mutates pass-1 subtrees; the graft
adds new siblings only.

Known limit (ponytail comment): a hardlink shared across the two passes is
counted twice.

### 8.2 Partial banner

While `isPartial`, every section shows a slim top banner: "Still scanning your
Documents, Downloads and Desktop — 41,200 files · 12.4 GB so far" with a
progress spinner. All sidebar sections are enabled.

### 8.3 Live buckets (`Core`)

```swift
public enum ScanBucket: caches, logs, developer, downloads, trash, backups, containers, other
public struct ScanProgress { files: Int; bytes: Int64; bucketBytes: [ScanBucket: Int64] }
```

Prefix rules relative to home: `Library/Caches` → caches; `Library/Logs` →
logs; `Library/Developer`, `.npm`, `.cargo`, `.gradle`, `.m2`, `.cache`, and
any directory named `node_modules` → developer; `Downloads` → downloads;
`.Trash` → trash; `Library/Application Support/MobileSync/Backup` → backups;
`Library/Containers`, `Library/Group Containers` → containers; else other.
A work item carries its bucket (inherited from its parent, otherwise matched
once when discovered). Files add to the worker's local `bucketBytes`; the
existing throttled progress path merges and reports them. The progress
callback signature becomes `(ScanProgress) -> Void`; `scan-cli` is updated
to the new signature.

### 8.4 Scanning screen

Shows "Step 1 of 2: hidden system files" / "Step 2 of 2: your files" (or
"Scanning <path>" for other scopes), the measured total, file count, and a
live list of the non-zero buckets with rolling numbers: "Caches 3.2 GB ·
Developer junk 5.1 GB · Downloads 8.4 GB · Trash 1.1 GB".

### 8.5 Main-thread stall

`SystemDataScan.build` shells out to `tmutil` for the snapshot count. The
rebuild of derived data moves to a background task and publishes on the main
actor, so the UI never blocks on it.

### 8.6 Tests (CoreTests)

- Two-pass graft on the fixture equals a single scan: sizes, file and
  directory counts.
- Bucket attribution on the fixture tree.
- Report built from pass 1 equals the report from a full scan for the Library
  rows.
- Cancel flag stops a scan early.

## 10. Release, App Store notes, order of work

### 10.1 Direct 1.0

- `CFBundleShortVersionString` 1.0.0, build 2. URL scheme `cleardisk` in
  `Scripts/Info.plist`.
- Commit the pending `make-app.sh` / `release-direct.sh` changes (universal
  binary, timestamped signature, signed DMG).
- `release-direct.sh` output DMG is copied to `web/public/ClearDisk.dmg`.

### 10.2 Mac App Store edition (next spec, not blocked by this one)

Xcode project with a second target; App Sandbox; home folder chosen once in an
open panel and kept as a security-scoped bookmark; no Full Disk Access flow;
no `tmutil`; no buy link, no update check (Guidelines 3.1.1, 2.4.5);
StoreKit 2 non-consumable at the $9.99 tier. Compile-time seams:
`LicenseStore` vs a `StoreKitLicense`, and the scan-scope picker. Listing:
name "ClearDisk", subtitle from the plan, screenshots in both appearances,
privacy label "Data not collected". Expect one rejection cycle.

### 10.3 Build order (each milestone leaves the app shippable)

1. Worker: routes, KV, key derivation, receipt signing, email; Stripe test
   mode; tests.
2. App: `RemovalSheet` + `TrashService` purge + result view; then
